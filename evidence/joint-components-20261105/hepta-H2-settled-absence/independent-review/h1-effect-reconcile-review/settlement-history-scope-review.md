# Settled absence remains a historical fact after legitimate reclaim

This is a source-only extension of the H1 root-cause review, bound to the same exact H1 source inventory. It is not a native test result.

Requiring the current run's final event to be the matching `requeued_proven_absent` event would fail safely, but it would leave a real recovery-read gap. `claim_taskflow_run` in H1 explicitly permits a run with prior provider attempts to be claimed again when all those attempts have proved absence and the run has been requeued. The replacement fence must have a generation strictly greater than the historical maximum and an owner epoch at least as large (`taskflow.rs`, lines 1026–1090). Claiming appends `lease_claimed`; starting the run or executing a later attempt adds further events. None of these legitimate operations erases an older attempt's proved absence.

With a final-event-only reader, the old absence lookup would return no fact after this legitimate claim. The host would then reconstruct the new mutable run fence and attempt to settle the old immutable step with it. The old step is `Reconciled`; `read_verified_step_tx` correctly requires the original step fence for that historical step, and would reject the new fence. This is a caller-visible availability defect, not a reason to weaken any fence comparison.

The narrow safe read is therefore historical. Inside one SQLite read transaction, first verify the complete current run and immutable event chain, load and verify the exact original step chain and cancelled receipt, and locate the specific original settlement event by the existing occurrence-derived `effect_command_id("requeue-absent", durable)` command ID. Require its transition and proof digest to match the original effect evidence. Do not infer settlement from the current run status or a later attempt's receipt.

The original command digest can additionally bind the settlement to the immutable original step fence without manufacturing authority. H1 computes `TaskFlowCommand::digest` as SHA-256 of `serde_json::to_vec(command)` (`taskflow.rs`, lines 628–666). A successful command increments the revision by one, records `command.now_ms` as `run.updated_at_ms`, and writes the canonical serialized transition as `payload_json` (lines 1318–1340). The event stores that updated time as `recorded_at_ms` (lines 1750–1805). Reconstructing the original command with the exact run/command ID, original step fence, checked `event.revision - 1`, exact `RequeueProvenAbsent` proof, and recorded time must produce the stored command digest. Negative or zero/underflowing numeric values must fail decoding; no saturating subtraction or current-fence substitution is appropriate.

This is a fact read only. It must not write, renew a lease, consume or restore a nonce, contact a provider, or make an old grant valid. Unknown, unobserved, durable-but-not-fully-settled absence, missing settlement history, and mismatched proof/intent/payload/fence must remain rejected or absent. The original live/fenced readers and append checks should retain their existing behavior.

The implementation owner has proposed this historical-event approach and a necessary successful read after legitimate reclaim. The actual patch remains subject to independent review and original-budget native execution.
