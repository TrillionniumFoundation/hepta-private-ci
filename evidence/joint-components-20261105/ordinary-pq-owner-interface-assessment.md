# Generic tool and model-provider PQ owner bridge

Status: **OPEN — source assessment only**. This supplements the existing ordinary-tool PQ audit at Hepta commit `1556a4df6e279055fd8196f81a4ca2fe0f19384a`, tree `9675a9e62a1fbbdaed3248eb239bb2036d79feba`. It changes no production code and claims no native qualification or complete sink inventory. The adjacent `ordinary-pq-owner-interface-sources.json` identifies the 21 files read and their exact Git blobs.

## Existing owner mechanisms can be reused

`hepta-contracts/src/final_use_pq.rs:12` already constructs a strict `MlDsa65V2` owner from pinned PQ issuer keys, a revocation head, host time and an independent CAS frontier. It refuses classical namespaces and a mismatched frontier. In `final_use.rs:273`, `VerifiedUseToken` is neither cloneable nor serializable and retains its owner. `enter` consumes that token, checks the exact binding, rechecks the live external frontier and time, and requires the current revocation head to equal the head authenticated when the claim was issued (`final_use.rs:334–365`; `final_use_live_owner.rs:38–56`). These mechanisms should be retained rather than replaced with an Allow boolean.

`with_verified_use_async` (`final_use.rs:773`) wraps an actual async consumer while holding an active-effect fence without keeping the owner mutex across await. Completion, panic or cancellation releases that fence. Revocation commits return `DispatchInProgress` while it is active. `with_dispatch_boundary` (`final_use.rs:818`) supports the narrower synchronous local handoff; its callback must return immediately and cannot wait for remote completion. The bridge must deliberately choose and preserve this entry/termination behavior. A callback that merely returns `Ok(())` does not itself carry the owner through a later effect.

`FinalUseBinding` contains subject, destination, request, scope and payload digests (`final_use.rs:53`). Agentd generation, logical operation identity, destination instance and finalized request semantics must be bound by the host's canonical request/scope construction; the current type does not have an explicit generation field. PQ authority epoch and revocation revision are additional owner checks, not substitutes for that host binding.

## A narrower final-use callback already reaches HTTP

`extension-api/src/contributors/model_provider_input.rs:83` defines the consuming `EphemeralModelInputFinalUseGuard::revalidate(self: Box<Self>)`. Its documented contract is source-currentness for an already-bound ephemeral proposal and explicitly excludes minting provider authority. Core retains the optional guard separately from the rendered content and consumes it at `core/src/client.rs:2154`, after the finalized provider-policy lease and before the HTTP single-attempt call. Failure records the admitted attempt as not dispatched before returning an error. The repository has a focused ordering regression at `core/tests/suite/model_provider_policy_http_ephemeral.rs:241`; this review did not run it.

The production `FederatedFinalUseGuard` (`ext/hepta-memory/src/cognitive/federation.rs:112`) revalidates the federated memory bindings, rejects a non-current result and checks the capability time window again after its asynchronous read. That is federation source-currentness. It does not consume a PQ `VerifiedUseToken` or authorize the whole provider request.

This hook offers an existing pattern for a one-shot, type-erased callback. Its coverage is limited to ephemeral HTTP input. WebSocket sends at `client.rs:2617` have no equivalent guard; active ephemeral contributors are deliberately routed to HTTP (`client.rs:2944`). Compaction has its own policy/physical-send path (`client.rs:896–929`). Other request kinds, sends without ephemeral content and non-provider effects still need their own complete path mapping. The audited callback's location before an API call also does not by itself prove that all later internal waits occur inside a PQ owner fence.

## Minimum interface boundaries that must change

| Boundary | Current behavior | Necessary bridge responsibility |
| --- | --- | --- |
| Tool policy API and lifecycle | `ToolPolicyDecision` is cloneable Allow/Block; `core/tools/lifecycle.rs` converts contributor results to `Result<(), FunctionCallError>`. | Return and retain an opaque, one-shot effect-entry capability from the required PQ owner; allow/block alone cannot carry it. Preserve aggregation failures and cancellation. |
| Tool dispatch and physical attempts | Pre-tool hooks may change payload before authorization (`registry.rs:657–690`). `ToolInvocation` is cloneable. The orchestrator later awaits approval/network work and can retry before `tool.run` (`orchestrator.rs:56–107`). | Bind the final authorized payload, carry the capability past waits without cloning it, and consume it at the selected effect boundary. Logical operation identity and each physical dispatch attempt must remain distinct. An owned handle or explicit one-shot take is needed; adding a token to a cloneable context is insufficient. Non-orchestrator sinks require separate mapping. |
| Provider policy and terminal owner | `ModelProviderPolicyInput` already contains attempt ID, stable request binding, endpoint/model/provider, logical/wire digests and optional input witnesses. `ModelProviderAttemptLease` only has consuming `finish`; its Hepta implementation persists terminal evidence. | Add a distinct entry phase or sibling capability and propagate it through policy composition, `AdmittedProviderAttempt`/`ProviderAttemptOwner`, and every physical send. Preserve existing NotDispatched/Indeterminate/terminal supervision and retry identity; a durable attempt lease alone is not a PQ grant. |
| Ordinary owner composition | Current ordinary governance installs Shadow with bootstrap integrity decisions; the generic API does not own PQ roots or an external frontier. | Inject the actual protected current PQ owner and its required host bindings through ordinary Agentd/app-server configuration. Reject missing/stale/downgraded authority at required sinks. Changing the mode enum cannot supply the missing capability. |

The dependency direction supports an opaque API: `codex-extension-api` currently has no `codex-hepta-contracts` dependency, while `codex-hepta-governance` already depends on both. A bridge can therefore implement a generic capability with the concrete PQ owner in governance/host composition. The API still needs to preserve a consumer-entry fence or proof to the actual sink; merely borrowing the ephemeral guard's name or returning success would leave the missing authorization relationship unchanged.

This is the minimum integration boundary assessment, not a ready-to-merge architecture. The independent frontier, issuer/root custody and concrete generation binding remain deployment/owner obligations, and every applicable sink still needs ordinary-path refusal and real execution evidence before the joint all-sinks PQ gate can close.
