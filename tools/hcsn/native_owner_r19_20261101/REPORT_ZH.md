# R19：原生恢复的请求身份与本机 TCP 丢回复

本轮修复 R18 原生客户端一个实际可复现的恢复缺陷，并加入有界 IPv4 本机回环 TCP 中继。R18 的数值状态仍按冻结帧重放；这不是原生金融核、跨主机网络认证或生产模型准入。

## 修复与原始失败

R18 的请求身份为 `PID + 从零开始的进程内计数器`，而 provider 的请求回复缓存持久存在。PID 再使用时，新的 LEASE 可以命中历史回复，得到旧代次。run01 实际原生基线重现了这一问题：先 fork 一个等待执行的 owner，用该 PID 的零号请求注入历史 LEASE，并再取得第二代租约；随后执行不变的 R18 二进制。它取得缓存的第一代租约，在 CHECK 处以 `stale owner generation` 退出，尚未产生计费效果。这里模拟的是历史 PID 身份别名，未宣称操作系统实际回收了 PID。

新客户端在同一个持久 mailbox 下锁定分配单调 `u64` 序号，并在发布请求前原子写入及同步序号。新身份使用 `0-序号`，与旧客户端的正 PID 身份区分。分配数据缺失初始化为零；数据损坏、溢出或已存在请求/回复冲突均失败关闭。本次试验要求保留该分配状态，没有对删除或回滚状态的恶意本机写者作保证。

TCP 中继只绑定 `127.0.0.1`。帧长度上限为 65,536 字节；读写有超时。实际效果继续由不变的 R18 Rust provider 原子落盘，完整请求和精确回复在同一提交中保存。断开连接不撤销已提交的计费效果；新 owner 使用原操作 ID 重试，由 provider 去重。

## 冻结与实际验证

源代码与协议先公开到提交 `d9bfd93d86a985dc603cce8b0c4ade6102cb7696`，经远端读取核对后才执行 run01。`SOURCE_FREEZE.json` 绑定所有测试源和四个不变的 R18 Rust 源文件。Rust 1.95.0 对基线及候选均以 `--edition=2024 -D warnings` 构建成功；二进制身份见 `BUILD.json`。

| 注册案例 | 实际结果 |
| --- | --- |
| 历史 PID 别名，原 R18 | 预期失败重现；退出 2，计费效果 0 |
| 同样别名，新客户端 | 完成；两个效果，总计 95 微费用 |
| TCP 正常执行 | 四种畸形帧及一个错误请求被拒绝；后续 owner 完成 |
| provider 已提交效果、TCP 尚未送回复时 SIGKILL 中继 | 原 owner 退出 2；重启中继和 owner 后完成，两个操作各计费一次 |
| 分配状态损坏 | owner 拒绝，效果 0 |
| `u64` 分配序号耗尽 | owner 拒绝，效果 0 |

第一轮 6/6 案例通过，共 16 个实际原生进程。三条完成路径均精确得到 cursor=5、clock=70、owner fee=95、provider count=2、provider fee=95，owner 收据与 provider 收据一致。TCP 负例后 provider 效果计数保持不变。完整状态、mailbox、进程退出、SIGKILL、stdout/stderr 及费用保存在 `results/run01/`。

外层 wait4 记录 Python 检查器和其已回收后代合计 **0.179 CPU 秒 / 0.629589296 壁钟秒**；内层 16 个原生进程 CPU 合计 0.092704 秒已包含于外层，不能再次相加。编译、开发和其他实验成本不在该运行数值内；单进程最大 RSS 不等于进程族峰值，也未测量能量。

## 尚未闭合

本轮仅资格化上述可信单机、有限帧、本机回环 profile。第二轮补充了分配提交与请求发布之间的真实进程死亡窗口（见下文）。没有断电、文件系统回滚、跨主机认证、TLS、持续攻击或完整生产生命周期证明。R18 provider 的 1,024 个回复容量界限仍保留。数值执行仍是冻结重放；真实模态采集、核心 D−B 增益、完整梯度、GPU／能耗和完整模型采用资格继续开放。`production_activation=false`，`all_blockers_closed=false`。

## 单独冻结的第七项：分配后、发布前死亡

第一轮全部六项、原始源和报告保存在 `source_v1/` 与 `results/run01/`，没有覆盖。V2 使用同一个 `allocate()` 完成客户端分配，另加一个独立 CLI fault role，在已同步的序号分配完成、尚未发布任何请求时暂停。V2 源和协议先冻结为 `1bcc1b2c9a1d3deaf7cfe9cdc928cfe8c28ee3fc`，随后执行 `check_v2.py`：先原样重跑六项，再运行第七项。

实际原生 allocator 在持有分配锁且 sequence=1、请求和回复均为空时被 SIGKILL。新的 owner 自动取得释放后的锁，从身份 `0-00000000000000000002` 开始，provider 回复身份精确为 2..9；身份 1 没有发布。最后依然只有两个计费效果、总费用 95，owner cursor=5、clock=70、fee=95。**V2 共 7/7 项、19 个实际原生进程通过。**

V2 外层 Python 与已回收后代成本为 **0.227708 CPU 秒 / 0.757346870 壁钟秒**，其中原生子进程 0.119761 CPU 秒已包含。两个不重叠活动合计 0.406708 CPU 秒；这仍不包含编译、开发和其他研究投资。`SOURCE_FREEZE_V2.json`、`BUILD_V2.json`、`PROTOCOL_V2.json` 和 `results/run02/` 保留完整身份与运行。

分配状态删除、部分备份恢复或文件系统回滚可能使计数器重新初始化，故这种恢复不在资格化范围内；provider 缓存幸存而分配状态丢失的组合仍属明确 blocker。
