## 实际数值与恢复语义

每个计划包含 PROP、READ、RESET、REFRESH、缺测和下一次 READ。所有操作具有明确的完整持续时间。RESET 先把内容边际送入恢复首相，再推进完整给定时长；READ/REFRESH 先推进完整时长，再用实际回执中的 token 做 Bayes 更新。参考程序通过独立 SciPy 矩阵指数重算这条轨迹，没有调用项目传播器。

owner 的入口不接收 CATALOG 或 REFERENCE 路径。provider 的实际 token 只有在请求之后返回，且回执必须同时匹配 run、模型、计划、索引、opid、动作、费用和顺序。保持同一公开模型与计划、只改变实际最后一次观测的控制，会改变实际 Rust 后验，并匹配另一条独立参照；这不是不透明后继带的重放。

owner 保存全部 40 个 FP64 位模式、已应用游标、整数纳秒时钟、已应用费用、回执及至多一个 pending 索引。准备阶段先持久化 pending；provider 先持久化实际计费效果再回复；owner 算出后继后，在同一次原子保存中提交后验、回执、游标、时钟和费用。重试同一公共操作身份返回已有回执，不重复增加账单。

每次新 owner 都以新的 TCP 流执行 SYNC，要求 provider 的前缀与本地已应用回执相同，至多领先当前 pending 的一个效果。删除 owner 但保留已付账单、删除 provider 但保留 owner 收据、修改模型、计划或观测目录都会拒绝。单机文件锁序列化同一指定路径下的 owner 调用。

一次不可能观测的注册坏例实际发生了 provider 费用 25；owner 的已应用费用仍为 0，但 pending 索引 1 和 provider 付费回执都保留。该情况是未完成的错误执行，费用没有当成 0，也没有算作成功恢复。完整执行中的 owner 和 provider 最终费用才一致。

## 修复可避免的版本身份缺口

最初工程版本仅用 MODEL 输入字节标识模型，不能防止同 schema、同三参数在构造器升级后被重新解释。本轮在正式冻结前修复：身份包含明确数值 ABI、原始输入、规范化的 2,000 个实际构造 FP64 字和准确可执行文件指纹。

实际添加非执行尾字节的 ELF 会生成不同身份，既拒绝旧计划，也在重新绑定计划后拒绝旧 owner 检查点；完全相同的 ELF 字节复制到另一条路径仍能成功续用原检查点。这些是准确的 artifact 控制，不冒称独立改变数值 ABI 的试验。FNV 是可信本机环境中的一致性校验，不是密码认证。

## 证据与成本边界

确认的完整 worker 为 **22.986995 CPU 秒／43.271371 壁钟秒**，包括导入、世界生成、独立参照、全部后代原生进程、控制和写证据。内部各进程计时另列，不重复加回。正式编译 0.855790 CPU 秒、独立记录审核 0.240085 秒，均单列。

六次工程活动原样保留，记录的 worker CPU 合计 14.894714 秒；前四次是旧的原输入身份配置，后两次是正式前的 artifact 绑定配置。旧执行源码、输入和结果没有被正式版本覆盖。以上非重叠已记录 CPU 下界合计 38.977584 秒，仍不包括所有早期编译、源码审阅、上层进程启动和运输成本；不是完整项目成本，也不是 Python/Rust 性能或能耗比较。

正式输出在 `confirmation01/`，协议在 `PROTOCOL.json`，独立程序在 `independentcheck.py`、`negativecheck.py` 和 `audit_records.py`。`INDEPENDENT_SOURCE_REVIEW.md` 给出前缀恢复的不变量和假设。先按运输与可执行文件还原说明恢复证据，再检查原始清单或运行只读审核器。
