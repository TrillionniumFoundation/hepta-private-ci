# Six versioned product qualification capsules, design only

## Purpose and consumer
Ship the six already independently qualified local Actor-selected Fashion interfaces as separate reproducible engineering capsules, not a combined runtime and not a new quality experiment. A developer can inspect exact source/receipts/reviews and explicitly materialize ONE candidate plus its pinned inputs into a fresh directory for later authorized qualification. Materialization never imports model modules, starts services, or runs a candidate. Existing RAW RUN trees remain original local evidence; the package must say which small receipts/reviews are copied and which raw saved evidence is only hash referenced. No false self-contained raw-audit claim.

Six versions: delivery-v2 (two requests and direct-reference parity), reconnect-v1 (real process death at acknowledged midpoint and zero recovery inference), live-control-v1 (sole-writer asynchronous cancellation and monotonic epoch), deferred-deadline-v1 (injected delayed return after real computation, not natural model timeout), active-channel-fault-v1 (actual EOF after acknowledged prefix, fault stays unknown), output-budget-outcome-v2 (typed known output-cap rejection versus prewrite unknown). Their individual scoped saved PASS records do not establish that every feature works in a single assembled implementation. Source and interpretation include original failures and costs.

## Evidence of need and version boundaries
INVENTORY.json pins all six original FREEZE/review identities and all runtime INPUTS. The union is only 13 paths/1,772,664 bytes. Core model, backend, route parser and thirteen common Python files are byteexact, but attempt.py and runners differ, with additional live wrappers. Do not replace all with a newest file. No migration of old request/artifact/source identities, no widening owner authority, no recovered unknown replay.

A shared materialized workspace would be WRONG: later candidates require delivery-v2/RUN_ONCE historical request/wire inputs, while rerunning delivery-v2 itself refuses an existing RUN_ONCE. Therefore each materialization targets exactly one capsule in its own new directory. It writes only the target's frozen source and its 7 or 13 pinned runtime input paths; other candidates' historical paths are data, not runnable jobs. The target RUN_ONCE must be absent. Future runner use retains original run-once, shared-lock and per-candidate limits. No automatic aggregate execution.

## Storage and actual consumption
First audit the runtime path closure from runner/supervisor/worker/common and compare with INPUTS; any undeclared file needed to run blocks claiming replay readiness. Copy original frozen files byteexact, including metadata. Copy selected source/saved reviews, findings, complete outer receipt, and prior-failure receipts/reviews as provenance; explicitly catalog which references are not copied. This latter catalog is not raw-result verification. All storage objects must be <=511999 bytes; no allowlist/workflow changes.

The only oversize runtime INPUT is content.npz, 1,560,407 bytes; gzip9 still1,475,632, so simple compression cannot meet policy. It contains78 stored NPY members. Preserve the exact archive as79 ordered raw ZIP records: each local-header-through-member record and the final4960-byte trailer (4938-byte central directory plus22-byte EOCD). Maximum record is401600 bytes. This is structural NPZ storage, not arbitrary JSON pagination; no interpretation or dtype conversion, archive mutation, recompression or training. Manifest binds original path/size/SHA256, each record index/offset/bytes/SHA256 and total contiguous coverage; records can be named by digest and deduplicated. A stdlib consumer verifies complete manifest/objects, exact order/coverage/whole SHA then reconstructs the original NPZ bytes. Record names remain safe digest identifiers; destination paths use explicit known capsule paths, no arbitrary archive extraction or symlink traversal. Other inputs stay exact intact files. Remote Git SHA/size and independently downloaded records must permit a full reconstructed content.npz hash check before release.

This preserves the exact existing native np.load consumer after reconstruction. No change to numpy/model serialization or claimed floating parity. Trust is local caller-selected immutable manifest, not production signature/owner authentication. Failures cannot overwrite existing directories; validation of all required bytes precedes output creation. OS/storage failures during final writes may leave an incomplete new directory, which must never be labelled usable. A completed materialization writes a final receipt last; rerunning against any existing directory refuses. No hostile concurrent filesystem guarantee or powerloss transaction claim.

## Validation and bounded execution proposal
Before tests: freeze implementation, exact capsule allowlist/mappings and reviewed artifact storage bounds; independent source and policy audit. Then one stdlib-only qualification under child CPU3s, wall15s, AS256MiB, file8MiB (original model/experiment budgets not reused or expanded). Reconstruct all six separate workspaces without invoking runners; all target frozen/source/input bytes compare to originals, target RUN_ONCE absent, record compressed/restore/hash CPU and all I/O counters by defined scope. Test wrong order, missing/duplicate part, bit corruption, incorrect size/digest, unsafe path, symlink, existing output, and partial directory without completion receipt. All failures occur before invoking any scientific code, so this is packaging qualification, not a new all-FIT/owner/reliability experiment. Keep preparation costs and full wait4 plus unknown outer tail.

Stop if the runtime closure requires unapproved/restricted files, if any blob exceeds limit, if original bytes/identities drift, if resources fail, or if materialization cannot produce an honest complete runtime input closure. Do not silently remove files, loosen limits, rerun or treat missing raw audit files as present. Scientific data403, denied App Server resources, strict256 and production permission holds remain unchanged.

## Publication
Independent validation precedes any remote mutation. Publish under a new versioned namespace on the original research branch using official GitHub plugin blob/tree/single commit/CAS, no merge/deploy/history rewrite. Only approved fixed artifacts, no credentials/personal runtime state. Actual repository checker must pass the incremental diff; the existing unrelated67 historical oversize blobs against main remain a separate blocker. This is a design, not source/run/publication admission, and no tests or candidate runs have occurred for this capsule scheme.

## Explicit fixed-entry and environment boundary

The closure is ONLY the six fixed run_once.py→supervisor/worker paths. multimodal_contract.py also contains a lazy legacy `serve` import for other RGB8 dispatch APIs; this is intentionally outside these Fashion entry paths and is not added to the capsule. No claim that arbitrary public functions in copied modules are usable, no new legacy/owner resource reads. Each materialized capsule must be invoked from its own workspace root so original relative INPUTS resolve.

A complete runtime-data closure is not a self-contained execution environment. Original runners require a caller-supplied, already-existing shared benchmark lock used by all authorized concurrent jobs; the materializer MUST NOT create a private replacement and claim shared exclusion. Existing compatible Python/NumPy and Linux flock/resource/fork/sched_setaffinity interfaces are required. Their installation, security settings, clock/owner authority and release environments are not changed or certified here. The packing test needs only stdlib, not NumPy.

Before implementation source freeze, record exact capsule manifest maximum bytes, number of object records, unique object bytes, all six expanded workspace bytes, each per-file bound, negative fixture counts and cumulative retained output bound. The proposed FSIZE8MiB is only a per-file limit, NOT total workspace/disk allowance. Any demonstrated total limit requires a separate explicit inventory check and its timing/failure scope, not a claim that RLIMIT_FSIZE enforces it. A source freeze without these totals is not ready for qualification.
