# Q24 original model material proposal owner

This candidate adds one durable owner between original Q24 training and a future
versioned Model Proposal route. It does not enable that route. The existing
production Parameter/Topology payload enum, Root profile, Selector and CURRENT
authority are unchanged; every returned material receipt has `DENY_ALL`.

## Why this owner is needed

The existing Q24 trainer can persist a changed quantized model and return its
original learning observation. A caller-supplied candidate digest or a cached
evaluation is not enough to establish a durable proposal. The new owner reads
the original trainer on every operation and binds its original evidence into
the proposal journal header. A different training result cannot be substituted
under an already initialized owner, even with the same Dataset and scope.

`CellQ24ModelProposalOwnerV1` accepts an explicitly transferred regular file and
an independently retained witness. The host remains responsible for directory
durability and for preserving the witness in a separate rollback domain. No
file path, witness, signer or role credential is generated by this API.

## Admission and recovery

- Require the exact original Dataset prefix, frozen scope, Training observation
  and evidence digest. Verify the current original Generator signature and the
  complete authenticated Generator principal used by evaluation.
- Validate complete candidate and baseline Q24 manifests. Invoke the existing
  signed evaluation adapter, retaining its independent controller and original
  execution/holdout checks. Only a qualified evaluation can create this record.
- Persist claim and completion through the existing exclusively locked journal.
  An uncertain witness acknowledgement fences the live owner. Recovery only
  reconciles already persisted suffixes; a pending claim remains pending.
- Recheck the independent witness after final receipt decoding. Warm and cold
  readback retain exactly the original bytes and observation timestamp. An
  expired operation can only read an existing record, subject to signatures
  still being valid; it cannot create a new one.
- Reject actual trainer `NoUpdate` before initializing a proposal file. Evaluation
  `Ineligible` or `InsufficientEvidence` cannot create a Model proposal either.

The exported learning receipt is material evidence. It has no original Proposal
role signature and cannot substitute for the governed production Proposal port.

## Validation record

The [result record](RESULT.json) and [source manifest](SOURCE_MANIFEST.json) bind
the reviewed source. Twenty source-closure tests passed (nine new owner controls, eight existing
evaluation controls and three existing TrainingNoUpdate controls), including unauthorized
caller insertion and removal of original training, Generator, evaluation,
journal, witness and timestamp checks. These controls are not native execution.

Seven native behavioral tests are authored. They run the original Q24 trainer,
file journal and signed evaluation machinery over explicitly synthetic task and
evaluator inputs. They cover unchanged training, evaluated NoUpdate, tampering,
expiry, warm/cold identity, four claim/completion acknowledgement fault cases,
a witness change after final decoding, and current host-clock verification
that rejects request backdating and expired original evidence. Native qualification is pending at
this checkpoint. The intended repository command is:

```sh
just test -p codex-hepta-agentd --lib --locked -E \
  'test(q24_model_proposal) | test(neuron_cell_evaluation::tests) | test(q24_training_owner)'
```

The initial dependency/build failures are preserved under `attempts/`. None of
the first three attempts reached a new test. The first lacked an uncached pinned dependency; the
second stopped in the AWS-LC bindgen build because Clang could not find its
resource headers. A later attempt supplies the original installed Clang
resource path, then stopped when rustc compiling `starlark` received SIGKILL.
The next combined run uses the original CI debug/incremental settings with one
job and two CPUs. No assertion, budget or failure outcome was relaxed.

The current integrated base already includes a necessary prerequisite: the generation-use exporter explicitly
rejects `TrainingNoUpdateV2` alongside all other non-use observations. An earlier merged
base omitted that new variant from an exhaustive match. A training outcome does
not become a completed NextUse or FinalUse through this repair.

## Remaining ordinary assembly

This is a material-owner stage across two small production modules, with
separate behavioral and source-boundary controls. It does
not register production callers; `CALLERS.toml` keeps the four entrypoints empty.

Production adoption still needs an explicit versioned Root Model profile and
payload route, current Dataset/withdrawal and artifact-frontier revalidation,
the original Proposal role attestation, and genuine Selector/publication/CURRENT
owners. Ordinary A task custody, independent B/holdout custody, a separately
authorized C task, and actual daemon plus Root exit/restart evidence must come
from their original owners. Matching hashes or synthetic fixtures cannot supply
those facts.

Production time comes from the owner clock, never `request.now`. Revalidation
uses the supplied fixed trust context; this component does not establish an
external live revocation registry or independent host custody.

Full ordinary-chain, positive-adoption, and NoUpdate/rollback acceptance counts
remain zero for this candidate. No policy benefit, independent consumer,
settlement, final use or production activation is claimed.

A hosted native build also exposed an existing undefined `pending` identifier in
the recovery tests. This candidate retains the unchanged-durable-state assertion
and compares it with its actual preceding `claimed` snapshot. That compiler
prerequisite is not a test PASS.
