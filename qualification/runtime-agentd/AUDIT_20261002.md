## Findings and required regressions

1. **Premature drain acknowledgement.** `state_drain.rs::drain_snapshot`
   checked App Server retirement, running turns, Automation blockers and provider
   workers, but did not inspect Agentd's own run coordinator. A dispatched or
   indeterminate compatibility run could remain while the public control protocol
   returned `drained=true`. Supervisor consumes that acknowledgement to advance
   retirement. The SIGTERM `drain_runtime` path already checks active/unresolved
   runs, so the two paths disagreed.

   `tests/run_drain_product.rs` starts the actual daemon and embedded App Server,
   submits two runs through public lifecycle ingress, transitions the real Fleet
   owner to Draining, retains both runs through cancellation-ACK expiry, then
   observes each terminal separately. Positive drain requires the actual App
   Server acknowledgement. It does not set an App Server test flag or run a
   substitute server. The lifecycle test does not claim physical Codex execution,
   authenticated terminal evidence, cross-restart recovery, or external effects.

2. **Predecessor cleanup removes successor rendezvous.** `control.rs::Drop`
   unconditionally unlinked its configured pathname. If the original socket was
   displaced while its listener remained alive, retiring it removed the successor
   socket, replacement regular file, or replacement symlink. The required behavior
   is to clean up only the same Unix socket object owned at bind time. This is
   orderly owner-cleanup protection within the trusted same-UID/operator namespace;
   it is not isolation from a malicious root/operator replacing paths concurrently.

   Four new real Unix-filesystem/listener regressions in `control_tests.rs` cover
   replacement socket connectivity, preservation of replacement file bytes,
   preservation of a replacement symlink and its target, and an already-removed
   original socket. Existing server shutdown coverage continues to require removal
   of the original owned socket. The existing architecture lifecycle lane runs
   all seven control tests (minimum seven passing tests) and the real daemon drain
   test (minimum one) before its separate runtime-image gate. The deep Agentd
   process suite also retains the new target. No gate is waived.

## Architecture and completion boundaries

Detailed development documentation exists in
`docs/modules/runtime.agentd/TECHNICAL.md`, `RUNTIME_EXTENSIONS.md`,
`AUTHBUS_TEXT.md` and the module dossier. The guide explicitly describes a
partial source inventory, not every exported method or a completed product.

Source inspection confirms these boundaries remain open:

- Ordinary startup embeds App Server and owner stores but does not construct an
  authenticated seven-owner invocation provider or production cognitive writer
  by default. CLI intelligence options construct only the runner.
- Canonical Objective preparation attaches context; it does not establish the
  full physical turn/start/interrupt/terminal chain.
- `RunObserveTerminal` remains the trusted local compatibility observation API.
  A boolean does not become independent physical terminal evidence.
- `recover_indeterminate` is a coordinator component API, not authenticated daemon
  recovery ingress. The run map is ephemeral; durable Objective publication is
  not a physical execution ledger. An absent/released run cannot authorize replay.
- Loaded executable-image proof, durable Decision/Outcome handoff, target-platform
  process acceptance, deployment receipts and independent acceptance are separate
  unfinished gates.

No activation, authority, deployment, promotion, or module-completion flag is raised.
