# Default Root CLI: original Initial publication

This source slice connects the default Root authority executable to the existing, separate Initial publication capability. It is based on `89b3b44747bedbc80732f73eda2405b7a397b926` (tree `1eba30f512a0fcd0463417c5f14537493cd8b104`). It does not change learned publication, create an issuer, or declare an ordinary task chain complete.

## Actual inputs and order

The trusted Root host supplies a version-1, UID0, single-link, exactly 0600 deployment file under an actual protected Root directory. Its strict data type is `InitialDeploymentData`. It contains the known initial operation and target observer configuration, existing target journal and witness paths, the original CURRENT directory, complete original Artifact trust and retained signed CURRENT/withdrawal floor, actual independently signed Model Selection, the fixed Device or Notes consumer root, the complete original issuer keyring, and one fixed trigger path.

There are no previous-generation, Learning checkpoint, or late-material fields. Unknown fields are rejected. The descriptor locates and pins original materials; its empty target configuration cannot assert that an actual journal has unwritten state or genesis. Original enrollment determines that from the original files.

The original CLI accepts these paired options:

- `--generation-initial-deployment <absolute Root descriptor path>`
- `--root-generation-initial-handoff-fd <distinct inherited offer FD>`

The caller must also provide the existing original Root pidfd and original consumer registration/owner pidfd. Fresh serving retains the original five-lane production handoff. Open-only serving retains its original inputs. The Initial offer descriptor shares the original single-claim set, must be distinct, and is marked close-on-exec by the original adoption code.

Initial and learned-publication options are rejected together before any FD claim, file open or enable. Both deployment/offer pairs are validated before the claim phase. A new Initial route does not require or invent a Learning checkpoint.

The CLI opens and retains the original descriptor and read-only file/directory identities, enables the actual Initial capability in the same original Prepared Root session, and sends its sealed purpose offer through the original ready callback. The callback emits and flushes `initial_deployment_session`. This is correlation data only. Listener readiness does not prove that the consumer has opened its nonce owners.

The trusted host waits for actual five-lane consumer activation before creating the fixed Root trigger. The trigger has one strict object, `{"session": <the exact emitted Initial session object>}`. It binds the independent Initial purpose, current Root PID/boot/start ticks, one checked process-local attempt and the exact retained descriptor digest. The host may not reuse an earlier session's object. The source refuses a missing, malformed, replaced or stale original, and never repairs or creates a consumer authority from this trigger.

After ACTIVE and a valid trigger, the same Root worker constructs the actual read-only target, Artifact view/Selection/files and consumer inputs. The Artifact reader independently checks the actual signed CURRENT and physical withdrawal view; the original enrollment still verifies the original full capability chain. The single-use capability invokes the existing same-service registration. Reserve and Recover remain explicit and never fall back to each other.

Only after registration and every file/path postcheck succeed does the worker immediately write and flush `initial_registered_binding` while the service is still running. That data ACK can sequence the daemon's actual purpose connect. The original returned registration is not execution permission. A post-registration observation or ACK-output failure is reported as uncertain; there is no automatic re-registration.

On service success, error, ready-callback failure or unwinding, the existing RAII stop guard stops the read-only waiter before thread joining. An already submitted registration waits only its original bounded reply. No second Root writer or issuer is opened.

## Reused safeguards

The exact original file/metadata algorithms are reused. Shared helper visibility is limited to their common `authority_host_runtime::session` ancestor; it is not public or general crate visibility. Metadata remains bounded to 65,536 bytes with original UID/mode/link checks, O_NOFOLLOW/O_NONBLOCK, actual directory FDs, full file stamps and post-read path/parent verification. Target and witness files remain read-only retained originals and may advance only under their actual writer.

The original Initial server still checks peer UID/PID/pidfd/incarnation, exact frozen target/scope/operation, original Artifact/Selection trust, schema3 consumer nonces/frontier and original signed FinalUse. Original CURRENT transitions, witness, cancellation, sticky fencing and uncertain-effect recovery semantics are unchanged.

## Remaining deployment facts

A deployment still needs its genuine original Root/consumer registration, protected directories and actual descriptors, original independently signed Artifact Selection and complete trust, existing consumer schema3 state, a real Model/target configuration, and the trusted host that can observe consumer activation and provide the one-shot trigger. These are not generated by the CLI. The daemon retains its original one-take connection and Initial/learned-offer exclusivity; the actual Initial consumer helper must use those capabilities and run the original task.

Ordinary complete chain, positive adoption, NoUpdate/rollback business chain, independently controlled consumer acceptance and physical Root/daemon cold-restart counts are all unchanged at zero. This slice adds a real default Root entry point and component assertions; it supplies no new ordinary acceptance evidence.
