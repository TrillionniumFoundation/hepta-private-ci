# Byte-BPE implementation and qualification boundary

The existing exact-body owner previously had only an external tokenizer ABI. `scripts/context_tokenizer/byte_bpe.py` now supplies an offline ranked byte-pair implementation and explicit provider-input interpretation. It does not infer an encoding from a model label and never substitutes byte length, character length, registered candidate costs or post-hoc usage.

## Artifact and ABI

The selected vocabulary is one `hepta.context-byte-bpe.v1` JSON artifact. It binds provider, model, version, normalization (`none` only), pre-tokenization pattern, mergeable ranks, special tokens and input framing. Rank entries are `{bytes_base64, rank}`; every byte must be present, ranks and byte strings must be unique, and special token IDs must be disjoint. Framing binds request prefix/suffix, explicit role prefix/suffix, the instructions role, an explicit non-input field allowlist and optional tool/structured-item serialization. Unknown roles, content types, fields and unqualified multimodal encodings reject. Duplicate keys, nonfinite numbers (including exponent overflow), incomplete regex coverage and excessive bounds reject.

Adjacent ordinary template/content text is concatenated before BPE. Literal special-token spelling in untrusted text is not interpreted as a control token. Only artifact-owned framing atoms can introduce special tokens. Provider-request mode counts the represented model input rather than the JSON escape length. Metadata does not become model input. This tokenizer is NOT the context-slot admission verifier; the separate strict framing verifier must still reject a canonical context that exists only in metadata.

The CLI accepts the existing `--provider`, `--model`, `--version`, `--vocabulary`, `--normalization` arguments. Default mode is `provider-request`; `--mode text` counts raw candidate/bundle bytes for the V3 compilation adapter. Standard input is the exact byte string. Standard output is only a positive decimal count; errors expose bounded reason codes. The external owner must retain its binary/vocabulary pins, complete I/O deadline, pre/post artifact checks and fresh post-tokenizer revocation check. The Python interpreter, dynamic libraries, regex implementation and deployment filesystem need an independently fixed runtime image; pinning this script alone is not complete runtime custody.

## Execution actually obtained

`python -B -m unittest discover -s scripts/tests -p test_context_byte_bpe.py -v` ran locally: **21 tests passed**, including 500 generated cases against a separate slow ranked-merge implementation, UTF-8/control/normalization cases, non-additive template boundaries, strict provider schema rejection and actual subprocess ABI tests. The exact tested code/test blob identities, environment and log digest are retained under `receipts/byte-bpe-local-20260927.*`. GitHub blob creation returned the same source/test hashes as those executed locally.

These use a small deterministic vocabulary to test the algorithm and ABI. They are NOT provider/model accuracy qualification, real-world latency/capacity measurements, a Rust build, product execution, current-head source/merge qualification or independent acceptance. No proprietary provider template, production vocabulary, signed approval or host performance number is invented here.

## Deployment gates

An independent owner must supply the actual licensed vocabulary, regex and special-token rules, exact provider/model template and tool interpretation, golden expected input-token counts, and pinned executable/runtime image. Unknown provider-internal framing must remain unsupported rather than be estimated. Run the existing immutable source-head and synthetic-merge qualification plus selected-host golden/capacity/revocation tests. No acceptance, activation, promotion or release flag changes in this implementation slice.
