## Decision

The existing public interfaces are sufficient to design a **same-boot, actual-process Root physical-state recovery and new writer admission component**: the original owner process exits, the original Root service process exits, an actual Supervisor admits a different owner into Starting, and a different Root service process restores the independently retained original physical state. This is a feasibility conclusion, not evidence that the composition has run.

That component must be reported separately from an actually running production daemon. A child which only receives the original five lanes and opens an original `AgentdConfig` has not supplied a Primary runtime or become a healthy Running daemon. The fixed default binaries also do not yet compose the physical-recovery and three-right writer handoff path. A full `AgentdProductionLaunch::run` test needs the actual selected Primary inputs and app-server/runtime path; there is no authorization to substitute a Ready flag, fake owner, or native image. [S21](https://github.com/TrillionniumFoundation/hepta-private-ci/blob/7666bcc2c650298f2e1d47e615a25864fe792fa1/codex-rs/hepta-agentd/src/production_launcher.rs) [S20](https://github.com/TrillionniumFoundation/hepta-private-ci/blob/7666bcc2c650298f2e1d47e615a25864fe792fa1/codex-rs/hepta-agentd/src/production_launcher_late_writer.rs) [S22](https://github.com/TrillionniumFoundation/hepta-private-ci/blob/7666bcc2c650298f2e1d47e615a25864fe792fa1/codex-rs/hepta-agentd/src/main.rs) [S23](https://github.com/TrillionniumFoundation/hepta-private-ci/blob/7666bcc2c650298f2e1d47e615a25864fe792fa1/codex-rs/hepta-agentd/src/bin/hepta-authority-host.rs)

This plan **does not close ordinary Q24 cold recovery**. The original retained-A capability and learning profile remain tied to real source custody and the original writer identity. A new PID/spawn cannot deserialize the old capability, reuse the fenced Root client, or change the old profile's writer proof. Actual machine reboot is a different case: the current adoption contract requires the same boot ID. ## Minimal actionable component plan

The smallest topology is an isolated, trusted controller P which remains alive, two **separate actual Root service processes** R1 and R2, and two **separate actual non-Root owner processes** D1 and D2. P owns the original Supervisor and the actual child handles/pidfds. Restarting P as well is outside this minimum, because a precreated driver cannot adopt its dead predecessor's in-memory queue. This topology is proposed test orchestration; it does not exist as a completed new test.

1. **Create original isolated state once.** Use the existing actual Root initialization and writer registration factories, real Fleet/Registry state, protected Root directories and separately authorized ordinary agent directories. Register D1 through the actual Supervisor driver/Starting transition. R1 uses `prepare_fresh_with_physical_material` once, followed by its original fresh filesystem handoff and sealed five-lane/triple-writer handoff. Do not replace fresh material with a JSON head or reuse the small publication fixture's synthetic learning history. The physical-state constructor is distinct from the current ordinary Root CLI's non-physical fresh constructor.
