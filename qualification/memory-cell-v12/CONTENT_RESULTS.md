# V12 WP2：真实字段内容、可访问性与存储成本

## 结论与范围

本轮完成 **18 个实际训练的模型臂和 9 个精确控制**。模型直接输出源文档声明的 owner、deputy、lifecycle 字段值，内容不是 record ID，也没有在预测后按 record ID 查询正确答案。所有模型在训练措辞上的完整三字段匹配率均为 100%；面对未参与训练的改写，单模型明显退化，固定分组的四个 cell 改善了结果，但部分 seed 发生错误接受。

**本轮没有取得相对精确 registry 的压缩优势。** 40 模块完整字段 registry 经 zlib 压缩仅 670 字节，并在支持的问题上全部正确。单模型原始参数为 68,392 字节，完整声明的 serving state 约 140.6 KB，而且持出回答不完整。不能把模型与近 1 MB 全文直接比较来宣称压缩获胜，因为模型仅提供三字段服务。

数据、源码和每例失败保留在 [完整结果](evidence/content/RESULTS.json)、[执行前计划](evidence/content/PLAN.json) 和 [逐文件清单](evidence/content/INVENTORY.json)。这些结果支持继续研究模块隔离、查询表示和校准，没有证明无限容量、自发结构演化或通用 memory system。

## 1. 来源、任务和冻结身份

来源是 40 份真实 `docs/modules/*/TECHNICAL.md`，固定 Git 提交为 `527218f9b823540830907f861a309310b71d38c9`。构建器逐文件验证 Git blob 身份，完整 corpus SHA-256 为：

`cbad82b9e82da96a26e3f8382a68816367a43c1d5827d35afa53494c6c3cadc1`

训练前冻结了协议、模板、源码哈希和来源身份；结束时重新检查，均未变化。实际执行版本在 [EXECUTED_SOURCE](evidence/content/EXECUTED_SOURCE/)。后续解析器或 optimizer 验证修复不应被冒称为本轮已执行版本。

目标字段有 20 种 owner、14 种 deputy、2 种 lifecycle，按排序码本编码为 5+4+1 个二进制输出。码本记录标签字符串，不记录模块到字段的映射。各规模使用同一 40 文档码本，这是已声明的共享标签词汇表，不是未知标签上的泛化。

模块按名称排序，使用前 10、20、40 个，形成嵌套子集。每模块有 3 个 train、2 个 calibration、2 个 test 模板。这些是作者编写的改写，不能当作生产用户问题。支持范围为：请求完整三字段，并包含唯一可识别模块名称。只问一个字段、未知模块或私人地址等属于本轮范围外。

owner、deputy 和 `existing/target` 都是文档声明，不是本实验核验过的部署事实。

## 2. 模型、信息与预算

输入为固定 lexical hash 的 word/character 特征，维度 256，没有预训练语言模型。hidden 和 head 参数均实际接受梯度训练。推理函数只获得参数、码本、公开地址和 query；精确 registry、源文档解析被明确允许读取其存储的字段，作为服务控制。

| 模型 | 结构 | 参数 | 总样本呈现 | 路由 |
|---|---|---:|---:|---|
| single | 256 → 64 → 10，ReLU | 17,098 | 600 × 32 = 19,200 | 单模型 |
| sharded | 4 个 256 → 16 → 10，ReLU | 17,128 | 4 × 150 × 32 = 19,200 | 公开模块名排序序号 modulo 4 |

这是固定分组控制，不是 learned router 或自发分裂。两臂看到同一原始问题，但 sharded 将显式解析出的地址用于选择参数分区，其增益不能单独归因于参数容量。

匹配的是总曝光，未强制逐地址曝光、CPU 或 FLOPs 完全相同。10 模块时四组为 3/3/2/2。三个 seeds `17041/17042/17043` 来自同一 corpus，不能当作三个独立数据集。

训练问题全部拟合说明：这些输入上的内容确实存入并可取出。本轮不能将持出错误直接解释为容量耗尽。更直接的瓶颈是陌生措辞如何访问内容，以及置信度在新措辞下是否可靠。40 模块 single 的 held raw exact 为 27.5%–35.0%，sharded 为 80.0%–90.0%，但精确控制均为 80/80。

### Calibration 零错误不是后续保证

阈值仅在 calibration 上选择：在零错误接受的候选中最大化 accepted-correct，平局取低阈值。没有用 test 标签选择。40 模块 single 三 seeds 都选到 0.99；sharded 为 0.65、0.55、0.65。

Calibration 满足选择规则，held 仍可能失败。40 模块 sharded/17042 接受 75 个支持问题，其中 71 个正确、4 个错误；对应逐例失败全部保留。

### Unknown 仅由显式 scope resolver 拒绝

10/20/40 模块分别有 14/24/41 个 held 范围外问题，所有臂全部拒绝。这来自独立规则：只承认公开表里的唯一模块，并要求三类请求词汇。规则不读取目标值，但提供了明确的任务边界。**不能把这些结果归因为模型学会了未知事实或任意越界意图检测。**

### 共享运行时与 CPU

Python 3.12.14 可执行文件实测 30,894,944 B，NumPy 2.3.5 包实测 40,782,533 B；冻结实验源码共 46,879 B。这些共享依赖单列，不能默认为免费，也不应对同节点每个 cell 重复全额计费。分摊应根据真实进程及依赖复用方式决定。NumPy 包不是全部系统依赖的封闭清单；标准库、动态库、操作系统、页缓存等未逐臂完整归属，完整进程 RSS 也没有隔离测量。本轮不声称提供了精确部署总 RSS。

实际总 CPU 为 2.220669 s，wall 为 2.244127 s。40 模块 single 的训练加 checkpoint 保存 CPU 为 0.1035/0.1054/0.1389 s，sharded 为 0.0642/0.0694/0.0722 s。一次共享特征编码为 0.02547 s；全部 362 个 train/calibration/test/unknown 问题的模型推理加 scope 解析约 0.0134–0.0149 s。每臂记录同一特征编码成本，是为了描述其服务路径，不能将共享编码反复加入真实总 CPU。

40 模块 zlib/lzma 控制的冷解压加全部查询分别为 0.03184/0.02223 s，原文冷读和结构字段解析为 0.01315 s。当前 registry 代码每题重复调用 scope resolver，模型路径只调用一次；这些短单次测量没有多轮计时，也不是完全相同代码路径的速度比赛。**不能据此宣称模型获得延迟优势。**

## 5. 文档冗余、答案低熵与外推限制

40 份技术指南使用重复标题和规范写作结构；本轮只提取每份文档头部三个短字段，其余约 954 KB 叙述没有成为待回答知识。文档总体长度不能作为 learned memory 的有效压缩分母。

答案来自有限词汇：20 owner、14 deputy、2 lifecycle；其中 `existing` 15 个、`target` 25 个，40 个字段三元组共有 36 种。相对开放文本，这是较低熵且结构受限的目标。码本、固定 bit 宽度、公开地址和路由都是设计的一部分，必须计入能力边界。

module 名称与团队名可能存在语义关联，query 也只有少量固定模板。本轮没有检验长事件序列、任意数值或引用精确恢复、多跳关系、跨类型组合、时间纠错、未见标签和生产会话。扩大同类模板数量不能替代这些任务。固定曝光下训练题全对，也不能替代收敛性、表示条件数、地址碰撞和更大规模容量分析。

## 7. 复现

保留原证据不覆盖，使用实际执行源码和同一 NumPy 版本：

```bash
OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1 PYTHONDONTWRITEBYTECODE=1 \
python3 qualification/memory-cell-v12/evidence/content/EXECUTED_SOURCE/content_experiment.py \
  --repo "$PWD" --out /tmp/hepta-memory-v12-content-reproduction
```

输出目录必须不存在。CPU/wall time 及包含计时的 receipt 文件哈希会随运行改变。复现和后续报告必须保留本轮错误接受、来源范围和成本边界。
