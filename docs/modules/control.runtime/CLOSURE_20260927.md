## Implemented source changes

The crate-root planner functions now route through `planner_boundary.rs`. The
boundary rejects summaries outside the required-owner cut, duplicate final
payloads, effect-bearing abstain, oversized resource/candidate projections,
clock reversal and owner observations that age out before finalization or grant
request. The original deterministic planner is retained rather than deleted.

`PlannerRequestBindingV1` binds owner identity, process generation, request,
query, retrieval profile, ranker, owner cut, read receipt, exact context and plan
receipt. `PlannerFinalUseLeaseV1` retains that digest under `Instant` with an
inclusive expiry and a maximum one-second lifetime. It is intentionally not a
serializable or client-reconstructible capability. The host must retain it and
must independently revalidate current owner authorization before final use.
The existing Agentd path has NOT yet been wired to this new lease.

## PlannerStoreV1 storage contract

The owner must provision a private directory and an independently durable,
authenticated `PlannerCheckpointAnchorV1`. An in-memory test anchor does not meet
that production contract. One persistent lock inode is held for the lifetime of
the handle, including checkpoint-file replacement. Files use private permissions;
symlinks and unexpected hard links are rejected on the Unix profile.

The version-one log header binds schema and store identity. Each frame carries
length and complemented length, sequence, kind, operation identity, decision
identity, predecessor, complete body and a domain-separated SHA-256 digest. The
store is bounded to 4,096 records, 1 MiB per body and 64 MiB per log.

A Decision body is a complete `PlannerDecisionEnvelopeV1`: codec digest plus
length-prefixed snapshot, prepared plan, NDU evaluation and plan receipt. A
versioned owner codec must validate the meaning of those component bytes. Storage
framing alone does not prove NDU correctness or authenticate a receipt producer.

Append ordering is:

```text
validate bounds and identity
  -> fence handle
  -> append complete frame
  -> sync log
  -> external checkpoint compare-and-swap
  -> update local projection
  -> clear fence and return record
```

An I/O error or uncertain anchor response leaves the handle fenced. Reopen loads
the current authenticated checkpoint, verifies every acknowledged frame and
replays the selection/revocation projection. Only tail bytes beyond that anchored
head are discarded. An acknowledged frame that is missing, truncated or corrupt
is an error; it is never reinterpreted as an empty store.

Backups are create-only, byte-exact and synchronized with their containing
directory. Restore publishes through a temporary file and atomic rename only
when the backup covers the CURRENT external checkpoint. Restore never rolls that
checkpoint backwards. Selection requires an earlier Decision, and revocation
prevents reselection across reopen and backup restore.

`checkpoint_file()` synchronizes and atomically republishes the exact committed
stream. It is NOT logical compaction. Logical retention, checkpoint rollover,
identity/revocation summary retention, schema migration and interrupted temporary
file housekeeping remain explicit implementation work. Unknown schemas reject.
Non-Unix durability and adversarial same-principal path replacement are not
qualified by this candidate.

## Added regression sources

`tests/planner_boundary.rs` adds five public-boundary cases: extra owners,
duplicate payloads, effect-bearing abstain, clock/freshness drift and bounded NDU
projections. Tests call the exported API rather than only its private kernel.

`planner_lease.rs` adds three cases: mutation of every request-binding field,
expiry and plan substitution, and zero identities/unbounded lifetimes.

`tests/planner_store.rs` adds seven cases: envelope byte completeness, restart and
idempotency, single writer, torn-tail/acknowledged-truncation distinction, frame
corruption, ambiguous anchor commit outcomes, and revocation/backup/schema
behavior. Some cases cover several assertions. These are test sources, not pass
receipts. Tail manipulation is not a substitute for child-process crash or real
disk-full qualification.
