# Qualification identity and readiness manifest

`memory.retrieval` has one machine-generated qualification fact:
`qualification-manifest.json`. The manifest is an observation of an exact Git
candidate and its GitHub Actions evidence. It is not a release approval and it
must never be assembled by copying green rows from unrelated workflow runs.

## Candidate identity

Schema `hepta.memory-retrieval.qualification-manifest.v2` binds:

- repository identity;
- source head and frozen source SHA;
- current protected `main` and base SHA;
- deterministic ordered-parent merge SHA and tree;
- GitHub synthetic merge SHA and tree;
- final merge SHA on a protected-`main` push;
- producer workflow run ID, run attempt, job, event, runner image and target
  triple;
- root source tree, documentation tree and qualification tree;
- `Cargo.lock`, qualification policy, product composition, production
  qualification and implementation-map hashes;
- the complete required-check profile and every relevant workflow-definition
  blob/hash.

A pull-request manifest is refused unless the GitHub merge has ordered parents
`base, source` and exactly the same tree as the deterministic merge. A
protected-`main` push is refused unless `source_sha`, `main_sha`,
`github_merge_sha` and `final_merge_sha` are the same final commit.

## One run and one attempt per workflow

Each required check is bound to its GitHub Actions job. The generator resolves
the job's workflow run, workflow path, exact source SHA and `run_attempt`.

For every policy workflow, the latest workflow run for the candidate is the
only eligible run. The current `run_attempt` of that run is the only eligible
attempt. Every required job belonging to that workflow must be present and
successful in that same cohort. Therefore:

- a successful job from attempt 1 cannot complete a partial attempt 2;
- checks from two workflow runs cannot be combined;
- a same-named job emitted by another workflow path cannot qualify;
- a job or run observed on another source SHA cannot qualify;
- missing, malformed or contradictory Actions metadata fails closed.

The manifest producer itself must be the selected
`hepta-memory-retrieval-convergence.yml` cohort. A manifest generated by a
different run or rerun attempt is not candidate identity evidence.

The required repository cohort includes the memory-specific source, merge,
host, maintenance and calibration lanes together with blocking CI, Agentd
process qualification, repository workspace preflight, ordinary-source
integrity and CodeQL. A missing, skipped, cancelled, stale or failed member
keeps `mergeReady=false`.

## Readiness states

The manifest deliberately separates three facts:

- `repository_checks_satisfied`: every repository-controlled cohort is complete
  and green for the exact candidate;
- `mergeReady`: candidate identity, repository checks and required security
  checks are satisfied;
- `productionQualified`: `mergeReady` is true **and** every independently
  governed external gate is satisfied.

External target-host measurements, a production encoder/index, external
frontier and revocation authority, tenant withdrawal/deletion qualification,
durable lifecycle/outbox recovery, held-out quality calibration, exact binary
identity, hard worker isolation, immutable/WORM retention, independent
acceptance, canary evidence, signed release evidence and formal approval remain
external facts. Their absence keeps `productionQualified=false`; it is not
rewritten as an internal source failure and is never fabricated by repository
tests.

## External evidence identity

A gate may use `state=satisfied_external` only with a bounded evidence object
containing `subjectSha`, `sha256`, `uri`, `signer`, `signature` and
`observedAt`. The policy loader rejects malformed evidence and rejects any
`subjectSha` that differs from both `sourceBase.commit` and
`observedAtHead.commit` in the implementation map.

The evidence subject is therefore the frozen implementation-source commit, not
an arbitrary earlier run. The immediately following map-only observation
commit binds that source to the exact candidate while avoiding cryptographic
self-reference. The exact-head source-integrity gate proves that the child
changes only `IMPLEMENTATION_MAP.json`; stale evidence, a mismatched tree, a
missing mandatory external gate or an unbound signature fails closed.

Repository validation checks identity and evidence shape. It does not claim
that a signer is independently governed merely because a string is present.
That governance and cryptographic trust-root verification remain part of the
independent external acceptance gate.

## Artifact handling

The convergence workflow publishes the manifest together with source and
deterministic-merge object receipts and a `SHA256SUMS` file. GitHub artifact
retention is repository evidence only. It does not satisfy the external
immutable-retention gate.

Every artifact name contains the producer run ID and run attempt. Consumers
must verify those fields against the manifest before accepting any receipt.

## Implementation-map observation

The implementation map uses the repository-wide
`candidate_or_exact_observation_v1` contract. Development changes are committed
first. The map refresh then sets both `sourceBase` and `observedAtHead` to that
exact source commit and records every mapped source/evidence Git object.

`observedSourcePaths` must not contain the implementation map or an ancestor
directory that contains it. Otherwise the second commit would attempt to attest
to its own future bytes. The canonical policy therefore enumerates map-adjacent
documentation explicitly and excludes `IMPLEMENTATION_MAP.json`.

The next commit must change only `IMPLEMENTATION_MAP.json`. Verification rejects
any drift in the enumerated source paths, any stale or incomplete source-object
inventory, an unknown identity policy, or a candidate whose map observation is
not its exact source parent. This two-commit representation resolves the
cryptographic self-reference without weakening source closure.

## Integration rule

Pull-request evidence belongs only to the pull-request head and its recorded
GitHub merge. It is not reused after integration. A push to protected `main`
runs the qualification workflow again and emits a new manifest whose
`final_merge_sha` is the actual merged commit.

The runtime manifest binds the map hash and the exact executing candidate.
Neither the map observation nor the manifest promotes a product, activation or
release claim.
