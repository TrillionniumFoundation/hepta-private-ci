# `learning.eval` target-host qualification

This document defines the external evidence packet required to move beyond
repository source qualification. It does not declare any host qualified. The
machine verifier is `scripts/hepta-learning-eval-target-host.py`; the authoritative
source status remains `CURRENT_STATUS.json`.

## Claim separation

Repository CI may prove that a candidate commit and ordered-parent synthetic
merge compile, pass tests, satisfy the coverage threshold and emit an attested
source artifact. Those facts do **not** authenticate a deployment host, establish
real future-calendar observations, prove storage semantics on the selected
filesystem, provide independent semantic acceptance, or authorize activation and
release.

A target-host packet uses schema
`hepta.learning-eval.target-host-evidence.v1`. It is supplied by the deployment
and independent qualification authorities, not generated by `learning.eval`.
The verifier rejects incomplete, self-colliding or overclaimed packets.

## Required candidate binding

The packet binds the exact candidate commit and tree, plus SHA-256 digests of:

- `codex-rs/Cargo.lock`;
- `codex-rs/hepta-intelligence-eval/PRODUCTION_CONTRACT.md`;
- `docs/modules/learning.eval/CURRENT_STATUS.json`.

With `--require-current-candidate`, the verifier additionally requires the packet
commit and tree to equal the checked-out `HEAD`.

## Host and trust evidence

The host section names the host and binds its OS/kernel, filesystem, clock and
resource-measurement profiles. The trust section binds the active trust
distribution, revocation snapshot and authority epoch. Remote request data cannot
construct these values.

## Storage qualification

The storage section must bind the final-holdout namespace, independent rollback
anchor store, qualification-publication store, evaluation-attempt journal,
fault-injection report and storage profile. A target-host claim additionally
requires evidence that:

- CAS is linearizable for the selected topology;
- committed transitions have the declared fsync semantics;
- the rollback anchor is retained independently;
- accepted-but-unknown publication is reconciled without duplicate semantic
  writes;
- stale writers are rejected after takeover;
- stale backup restore is rejected;
- crash recovery has been exercised;
- cross-host lock/fsync semantics have been qualified when cross-host use is
  claimed.

The repository locked-file backend is directly qualified only for its tested
single-filesystem behavior. A shared filesystem must supply its own cross-host
linearizability and durability evidence.

## Longitudinal, privacy and unlearning evidence

At least two non-overlapping, real future-calendar windows are required. Every
window binds start/end/observation times in Unix microseconds, a positive observed
count, a distinct source cut, outcome evidence and an independent observer
attestation. At least three distinct snapshots are required. The packet also
binds retention, change-point, power, subgroup/privacy, unlearning and backup
non-resurrection evidence.

Synthetic IDs, virtual time and repository test fixtures do not satisfy this
section.

## Independent acceptance and authority

Generator, evaluator, observer, semantic reviewer, operator, selector and release
principals must be pairwise distinct. The packet binds separate semantic
acceptance, operator acceptance, canary, selection, promotion and release
authorization digests.

Claims are monotone:

1. `targetHostQualified` requires all storage qualifications;
2. `independentAcceptance` requires target-host qualification;
3. `productionQualified` requires both;
4. `activationAuthorized` requires production qualification;
5. `releaseAuthorized` additionally requires activation authorization.

The verifier never changes a false claim to true. It only confirms that a
supplied true claim has all required evidence fields and ordering constraints.

## Verification

```bash
python3 scripts/hepta-learning-eval-target-host.py self-test
python3 scripts/hepta-learning-eval-target-host.py verify \
  evidence/learning-eval-target-host.json \
  --require-current-candidate
```

The resulting verification receipt is structural and candidate-bound. Signature
verification, issuer authorization and artifact retrieval remain responsibilities
of the external evidence authority and selected host trust profile.
