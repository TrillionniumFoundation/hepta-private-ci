# kernel.evidence readiness manifest contract

`READINESS_MANIFEST.json` is the only repository-controlled readiness object for
one immutable `kernel.evidence` candidate. It is generated by
`.github/workflows/kernel-evidence-readiness.yml`; checked-in status files and
historical qualification archives are provenance only.

## Exact identity tuple

Every required receipt and retained artifact belongs to one tuple:

- source head commit and tree;
- immutable base commit;
- deterministic two-parent merge commit;
- GitHub synthetic merge commit when the event supplies one;
- workflow definition commit;
- final real merge commit on the post-merge run;
- workflow run ID and attempt;
- runner image and target triple.

The manifest also binds `Cargo.lock`, the discovered test set, migrations,
current generated implementation map, documentation and every named retained
artifact by SHA-256. A result from a different commit, tree, base, workflow,
run, attempt, runner or target cannot be assembled into the candidate.

## Required candidate receipts

The exact-source, deterministic-merge, metadata and publication-diagnostics
receipts are mandatory. The deterministic-merge lane executes both the Rust
product tests and the same closed-world metadata, documentation and generated
implementation-map validation used for the source head. A green source lane
cannot substitute for a failed or absent merge lane.

Receipt JSON is not trusted on declaration alone. Before finalization,
`kernel_evidence_receipt_audit.py` reopens the retained logs and verifies:

- strict integer timestamps, byte counts and exit codes; booleans are rejected
  even though Python compares `False == 0`;
- the exact expected log path, with no symlink traversal or non-regular file;
- actual log byte count and SHA-256 against the receipt;
- exact candidate and workflow identity;
- terminal success and false self-issued authority fields.

The 12 crash-consistency scenario receipts receive the same byte-level audit.
For every command, the audit checks the canonical argv rendering, retained log,
required success markers, absence of skip markers, digest, size and strict
terminal exit status. `SUMMARY.json` must contain the exact closed-world
scenario inventory and must bind each scenario receipt's actual bytes.

## Two-stage fail-closed construction

The workflow first writes `READINESS_MANIFEST.preliminary.json` and the runtime
`STATUS_SOURCE.json`. `kernel_evidence_finalize_readiness.py` then binds the
receipt-audit object, updates the runtime-status digest and emits the final
`READINESS_MANIFEST.json`.

Any absent, malformed, mixed-identity or byte-mismatched receipt forces all
aggregate repository-controlled readiness fields false and adds
`receipt_audit` to the blocker set. Individual diagnostic results remain visible
but cannot produce a green aggregate. The final policy gate requires the audit,
artifact inventory, crash matrix and all four candidate receipts.

## Post-merge rule

PR-head, deterministic-merge and GitHub synthetic-merge receipts do not qualify
the eventual real merge object. A push run on `main` must use the real merge SHA
as both source head and `final_merge_sha` and must rerun the complete contract.
Until that succeeds, `final_merge_requalified` remains false.

## Authority boundary

Repository implementation and hosted execution do not grant independent
acceptance, authenticated external-authority deployment, target-host durability,
operator activation, canary acceptance, promotion or release. The manifest and
runtime status force each of those fields false unless a separately governed
system consumes distinct retained authority receipts; this repository workflow
does not manufacture them.
