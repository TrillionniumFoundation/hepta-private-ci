# Kernel evidence recovery frontier V2

The filename is retained for existing links. V1 records are no longer admitted.

This document defines the required anti-rollback and complete-database
replacement contract for `kernel.evidence`. It is a required activation
ceremony. Repository source can validate and bind these records, but an external
frontier is not created merely by writing another row into the same SQLite
database.

## 1. Threat model

A valid SQLite image can still be stale, replaced, copied from another host or
restored behind a revocation/correction frontier. `PRAGMA quick_check`,
migration checksums and canonical row digests detect local corruption; they do
not prove freshness against an attacker or operator holding an older complete
database image.

The anti-rollback witness must therefore live in a rollback domain independent
from `hepta_evidence_2.sqlite`.

## 2. Signed frontier record

The external checkpoint service stores one append-only/CAS monotonic
`EvidenceRecoveryFrontierV2` per evidence store. The checked-in Agentd profile
accepts a strict versioned JSON record with:

- `schemaVersion = 2`;
- `storeId`: random enrollment identity generated by the checkpoint owner,
  never derived from a path;
- `frontierGeneration`: strictly increasing unsigned integer;
- `snapshot`: `EvidenceRecoverySnapshotV2` containing:
  - `schemaVersion = 2`;
  - `databaseLineage = "hepta_evidence_2.sqlite"`;
  - `migrationSetSha256`: rolling digest over ordered successful migration
    version/description/checksum tuples;
  - `qualificationMaxSeq`: greatest `qualification_evidence.seq`;
  - `qualificationFrontierSha256`: rolling digest over ordered
    `(seq,evidence_id,envelope_sha256)`;
  - `authbusReplayFrontierSha256`: rolling digest over the complete bounded
    AuthBus replay high-water projection;
  - `providerEffectRows`: total retained intent, uncertainty and ACK rows;
  - `providerEffectFrontierSha256`: ordered commitment to each table identity,
    sequence, stable effect key, record digest, `recorded_at_ms`, and
    ACK source provenance. The scan is paged and fails above one million rows;
- `sourceCommit` and `sourceTree` for the source qualification object bound
  by the checkpoint publisher;
- `createdAtUnixMs`;
- `signerPrincipalId`, `signerKeyEpoch`, and `signatureHex`.

The Ed25519 signature covers a domain-separated, length-delimited binary
preimage in `hepta.kernel.evidence.recovery-frontier.v2` produced by
`evidence_recovery_frontier_signing_bytes`; it does not
sign its own signature field. The signer is not the evidence-store process and
its key material is not stored in the evidence database. This authority remains
Ed25519; V2 does not add PQ identity authentication.

All snapshot components are read in one SQLite transaction. Within it, effect
record digests are rechecked against the actual stored JSON bytes; retaining a
digest while replacing its JSON is refused. V1 snapshots omit provider-effect
history and cannot be upgraded from a recovered local database; the checkpoint
owner must review and sign a new V2 checkpoint.

## 3. Backup publication protocol

One admissible backup is created in this order:

1. Fence new product writes and wait for current SQLite transactions to finish.
2. Produce a transactionally consistent SQLite backup image.
3. Re-open the image read-only and run migration-ledger, schema-manifest,
   canonical qualification-row, lineage and foreign-key verification.
4. Compute the migration-set, qualification, AuthBus replay and provider-effect
   frontier digests from the same SQLite snapshot.
5. Read and authenticate the latest external frontier.
6. Create generation `N+1` with the same `storeId` and compare-and-swap it
   against the complete expected checkpoint `N`, including its history digest.
   Require an append-consistent extension; a larger counter alone is insufficient.
7. Require durable acknowledgement from the independent checkpoint service.
8. Only after step 7 may the image be labelled an admissible production backup.
9. Unfence product writes.

A timeout, lost acknowledgement, signing failure, CAS conflict or uncertain
external durability after step 5 is **recovery_required**. The procedure must
re-read the external frontier before retrying; it must not guess whether the
generation was committed.

## 4. Startup and restore admission

Before admitting any restored database for product reads or writes:

1. Fetch the current frontier and signer trust from the independent rollback
   domain.
2. Require both files to be canonical regular files outside the Agent home,
   bounded in size and not writable by group/other; fail if either changes
   during read.
3. Verify current signer principal/key epoch/revocation and strict Ed25519
   signature.
4. Re-open and verify all local SQLite integrity invariants.
5. Recompute the migration, qualification, replay and provider-effect snapshot
   from the restored image.
6. Require the local snapshot to equal the externally signed snapshot exactly.
   The checked-in profile is intentionally stricter than an "at least"
   comparison: unpublished later writes also require publishing a fresh
   frontier before restart.
7. On first successful enrollment bind `storeId` into the immutable singleton
   `evidence_recovery_identity`; on later starts require exact identity match.
8. Reject a complete database that has a valid SQLite structure but a different
   identity or frontier.
9. If equivalence cannot be proven, enter **recovery_required** before the
   evidence host becomes available.

A restore behind an externally observed revocation/correction is never repaired
by treating missing rows as absence of the revocation. It is rejected.

## 5. Retention and non-resurrection

- Base evidence, corrections and revocations are append-only.
- An externally committed frontier generation is never deleted or overwritten;
  backend retention may compact old generations only after an independently
  auditable successor chain is preserved.
- Backup retention must cover the evidence retention horizon and at least one
  previously accepted predecessor generation.
- Deleting evidence, replay high-water, provider-effect or checkpoint history
  must never turn missing state into positive proof.
- Restoring an older binary is allowed only when it can read the current
  migration lineage and validate the current external frontier; otherwise
  rollback requires a forward recovery binary.

## 6. Backend requirements

A production checkpoint backend must provide authenticated reads, conditional
write/CAS, durable monotonic generations, signer/key rotation with revocation,
and a rollback domain independent from the local evidence filesystem. Examples
of deployment classes include an HSM-backed service or version-locked remote
object store plus signing service; this document intentionally does not declare
a concrete provider.

The repository now contains the local snapshot algorithm and Agentd signed-file
startup/restore verifier. That source path proves how a current independently
retained frontier is consumed; it is not itself the monotonic external service.

Until a durable backend providing authenticated *latest* reads, monotonic
generation/CAS and durable acknowledgement is selected, qualified and wired
into the backup publication ceremony, the implementation map must keep
external anti-rollback activation unproven.

## 7. Required qualification faults

Production qualification must inject at least:

- crash after SQLite backup but before frontier CAS;
- crash after CAS request but before acknowledgement;
- frontier CAS conflict;
- stale/rotated/revoked checkpoint signer;
- complete database replacement with a valid older image, including an image
  missing only provider-effect rows (negative Agentd product fixtures compare
  these images against a newer signed frontier);
- restore behind a correction/revocation;
- missing external frontier;
- corrupted backup image with a valid older frontier.

Every ambiguous post-CAS outcome ends in `recovery_required` until an
authenticated frontier read resolves it. No fault path may manufacture a
supported evidence disposition.

## 8. Scope and unresolved deployment requirements

The checked-in admission path verifies externally supplied signed files; it
does not implement the remote service, authenticated fresh fetch, expected-old
CAS, or durable co-signing described above. A canonical path outside Agent home
does not prove an independent failure domain. If both the database and those
files roll back together, the older valid signature remains valid.

Provider-effect coverage here belongs to the `hepta-evidence` qualification
facade. It does not cover the separate AutomationStore effect owner, compose
FinalUse consumption with its budget and effect journal, or authorize a new
provider call. Unknown outcomes must retain the original stable operation
identity. A production deployment must retain independently fresh state and
stop affected new operations when that state is unavailable. The witness has
neither PoN fork-choice authority nor permission to issue business grants.
