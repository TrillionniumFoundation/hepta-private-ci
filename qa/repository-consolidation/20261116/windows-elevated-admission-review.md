This safety correction is separate from the reviewed PR #6396 merge `915b2db8dc11767dff956111871715aee4d2165d`. It makes the elevated backend unavailable until a functional replacement is qualified. It does not establish the original permission invariants and is not a reason to waive the existing required gates.

`ElevatedWindowsSandboxIsolationUnavailable` now propagates from the raw elevated token constructors, elevated capture, the explicit elevated session path, and the generic elevated-level dispatcher before capability persistence, provisioning, ACL changes or child launch. The command runner independently applies the same admission check before hiding the current user's profile directory or creating a token. The core capture caller already returns the spawn error; this change adds no unrestricted retry or fallback.

The original token flags and restricted SID composition remain intact behind admission. No environment override, test-mode production bypass, new capability grant, or broader group SID was added. The existing successful-launch, network, custody, cancellation and four-cell delete assertions remain unchanged and can legitimately fail while functionality is unavailable.

Three new Windows regression methods exercise both raw constructors with a live token, capture with read-only/workspace-write profiles, and direct/generic sessions across every tty/stdin combination. Capture/session checks compare the complete owned fixture snapshot including bytes and DACLs, detecting home creation or child execution. The native observation workflow adds these three distinctly identified refusal methods without replacing its original ten ACL methods or six Python methods; zero skips/retries and exact source identity checks remain required. Its permission qualification remains false.

## Minimal functional replacement plan: proposed, not implemented or qualified

1. **Use a separately reviewed full-restriction mode.** Microsoft documents that restricting SIDs participate only in write checks with `WRITE_RESTRICTED`, whereas ordinary restricted tokens require both normal and restricting-SID access checks. The Windows file-open algorithm separately permits DELETE through the parent's FILE_DELETE_CHILD. Native owned-object probes are useful evidence for removing the flag but do not demonstrate production process compatibility. [CreateRestrictedToken](https://learn.microsoft.com/en-us/windows/win32/api/securitybaseapi/nf-securitybaseapi-createrestrictedtoken), [file-open access algorithm](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-fsa/82b364ce-6d7b-422f-8d88-4db32eea809a).

2. **Provision read/execute rights for the actual restricting identities.** `src/bin/setup_main/win.rs::apply_read_acls` currently skips sandbox-group grants when an ambient Users/Authenticated Users/Everyone ACE permits reading. That proves only the ordinary pass. Full restriction needs explicit read/execute capabilities for selected read roots and runtime inputs, including the mapped synchronization rights, with no write/delete/ACL-owner grant. Fail on unprovisionable roots instead of adding broad restricting SIDs. Broad recursive system ACL edits require a separate lifecycle/rollback design. [File security and access rights](https://learn.microsoft.com/en-us/windows/win32/fileio/file-security-and-access-rights).

3. **Prove executable, DLL and object access during real launch.** CreateProcessAsUser requires read/execute access to the executable and appropriate window-station/desktop rights. Filesystem read grants alone do not establish access to every registry, cryptographic or named object touched during startup. Retain the private desktop requirement and test ordinary program initialization, DLL loading and CNG/IPC behavior with the exact token. Preserve the inherited-handle allowlist and no Backup/Restore/ownership privileges. [CreateProcessAsUser](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessasuserw), [restricted token desktop requirement](https://learn.microsoft.com/en-us/windows/win32/secauthz/restricted-tokens).

4. **Scope IPC separately from filesystem authority.** `runner_pipe.rs` grants its broker pipes to the dedicated sandbox user; `token.rs` keeps that user among restricting SIDs for owner-scoped IPC and deliberately excludes network route markers from the default DACL. A full-mode design must keep IPC working without letting a user/group/route ACE authorize arbitrary outside-root writes. Audit sandbox-user-owned outside-root files as well as Everyone-based fixtures. Use exact object rights; generic pipe write rights also permit creating pipe instances. [Named pipe security](https://learn.microsoft.com/en-us/windows/win32/ipc/named-pipe-security-and-access-rights), [token default DACL](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-token_default_dacl).

5. **Require the original native acceptance evidence before reopening admission.** Run the original four-cell matrix through the actual elevated child, all permitted-root positive controls, readonly/write-root overrides, deny-read/protected paths, capability and network identity checks, private-desktop behavior, ConPTY/stdin and all broker custody/cancellation tests. Include dedicated-user parent rights, inherited/protected ACLs and replaced/reparse paths. Record exact source head, original methods, raw outcomes and zero skips/retries. A refusal-only result or owned-object token experiment cannot authorize reopening the backend.

These steps are a code-review plan inferred from the current provisioning and token composition; the cited platform documentation does not certify this implementation. The safety guard remains until real native results establish both isolation and required functionality.
