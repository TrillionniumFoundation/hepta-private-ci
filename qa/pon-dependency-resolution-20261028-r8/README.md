## One-shot proposal lifecycle and corrected trigger assumption

The preparation used a restricted PR trigger to generate the first proposal
before dispatch registration on a default branch. After its artifact was
retrieved and reviewed, the coordinator initially assumed that placing this
follow-up evidence in a new QA directory would avoid triggering it again. That
assumption was incorrect: GitHub evaluates PR `paths` using the cumulative
three-dot PR diff, which still contains the earlier proposal workflow and script.
The correction was accepted before this candidate was published.

The [official path-filter documentation](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow#git-diff-comparisons)
and the PR/source readbacks are retained in `trigger-lifecycle-review.json`.
This candidate therefore retires only that completed, non-qualifying proposal's
`pull_request` automatic entry point. `workflow_dispatch`, its required exact
SHA, all source validation, read-only permissions, credential-free checkout,
timeouts, failure recording and final dirty-tree guard remain intact. Every
original qualification workflow, owner and native acceptance denominator is
unchanged. No branch-protection setting is changed.

The historical PR and dispatch source positive/negative controls remain. A new
behavioral control confirms that attempting another proposal against the already
applied manifest fails before native command execution, retains the incomplete
preparation record, and leaves the inputs unchanged. The manual path has not
been converted into a success/skip fallback. Its actual rejection remains an
error if it is invoked with the applied graph.
