# Hepta shared-Encoder / Cell CPU reference — non-production

This package records actual calculations executed in ChatGPT's isolated Linux CPU container on 2026-10-22. It is **not** the user's dot machine, the Hepta Rust/production inference backend, a pretrained Encoder, or an external-model evaluation. No live tool effects, real CAS/CNS/FinalUse, or target-host operator acceptance are exercised.

## Reproduction

Requires Linux, Python 3.13, PyTorch 2.10 CPU, NumPy 2.3, psutil. All input arrays and teacher parameters are deterministic synthetic tensors.

```bash
python3 -m unittest discover -s . -p 'test_bench.py' -v
python3 bench_shared_cell_cpu.py --repeats 80 --out cpu_reference_measurements.json
```

The experiment creates two computation implementations for each of 1, 8, 64, 256, 1024 and 4096 logical cells:

- **shared:** one 64×64 frozen encoder computation with vectorized Cell heads;
- **duplicated:** independently materialized copies of the identical 64×64 encoder for every Cell, with a batched matrix multiply.

Both methods consume the same synthetic input and same frozen numerical parameters. They are expected to agree up to rounding. Each cell-count/arm measurement runs in a separate disposable subprocess and collects 80 p50/p95/p99 latency samples, observed RSS, and exact float32 parameter-byte counts; subprocess setup and Python import are **not** included in inference latency.

A separate 8-Cell synthetic teacher regression performs 160 actual Adam steps on a frozen shared feature matrix and evaluates on separately generated synthetic samples. NoChange/zero-delta numeric parity is also checked. This does not show independent real-task learning or lack of negative transfer.

## Important caveats

- `shared` and `duplicated` are deliberately unequal compute designs; this benchmark illustrates the resource difference from repeated base work. It is **not** a fair end-to-end quality, accuracy, hardware-utilization or MoE experiment.
- The dynamic benchmark timings varied notably between successive container runs; infer no production p95/p99 or statistical speedup guarantee from a single report. A proper study needs repeated host-pinned runs with CPU/NUMA isolation and confidence intervals.
- Linux `fork` is used for disposable numerical children to keep turnaround bounded. CPython issues a multi-threading warning; this is a sandbox-only numerical microbenchmark, not a production subprocess isolation design.
- The report includes `reference_only=true`, `p2_production_qualified=false`, `p5_production_qualified=false`, `independent_target_host_observer=false` and `signed_production_receipts=false`. Do not import this artifact into Hepta's production evidence registry or label it an independent measured target-host acceptance packet.

For real P2/P5 closure, execute the actual frozen pretrained encoder + learned heads through Hepta's Rust runtime on the target hardware under approved source/toolchain and independent observer, with the full no-change/fixed/learned-routing and shared/duplicated baselines, physical receipts, budget/negative-transfer, crash/reopen, CNS/generation/fence and p95/p99/RSS/GPU/CPU/WAL results.
