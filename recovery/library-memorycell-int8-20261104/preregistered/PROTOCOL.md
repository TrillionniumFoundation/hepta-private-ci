# Preregistered, bounded CPU INT8 engineering screen

**Status: preparation only. No real-model run, dependency installation, weight download, or model-output inspection has occurred in this preparation task.** The fixed source and fixture hashes are in `seal.json`. This is a new engineering screen, not a rerun of any historical experiment. The earlier JSON-reader 0/8 result stays closed.

## Question and interpretation

On one authorized Linux x86_64 CPU host, does exactly one dynamic-qint8 Linear candidate meet a prospective numerical/ranking agreement and cost policy against the fixed FP32 cross-encoder? This can establish only whether these finite fictional inputs pass this engineering screen on this host. It cannot establish retrieval quality, relevance, memory/task utility, generalization, production suitability, or training improvement. Nothing is trained. No candidate search, benchmark copying, historical train/dev/held-out examples, or sealed72 material is permitted.

The reference is `cross-encoder/ms-marco-MiniLM-L6-v2` at revision `233902d25c440f23af6f7d6e94d2946bac0bee0a`; required `model.safetensors` SHA-256 is `821d1aa69520101d6e0737f78a042ae25b19e5cb9160701909d10434f4aeb0ae`. ## Fixture fixed before model access

`fixtures.json` is the complete original fictional input, exactly reproduced by `fixture_builder.py`. There are 12 queries, each with four passages: 48 query/passage pairs. Four queries each have short, medium, and long passages of exactly 48, 112, and 224 whitespace words. Queries contain at most 24 words. Padding is a fixed original fictional archive description, not sampled from any source. Two queries contain exactly duplicate passages to expose tie handling. There are no relevance labels; plausible semantic content is not truth for this screen. A model-generated or manually inferred label must never be added.

All 48 pairs are used, with no exclusions or adaptive changes. Maximum encoded length is 384 tokens, longest-first truncation. Report actual untruncated lengths and any truncation; never relabel the word-length strata as token strata. Each request is one query and its four passages, dynamically padded together. Token ID fingerprints must match across all sessions.

## Fixed implementation and runtime

- Python 3.12, PyTorch `2.5.1+cpu`, Transformers `4.57.1`, safetensors `0.6.2`. Full resolved dependency versions and SHA-256/size of every declared installed distribution file (including native binaries and any installed bytecode), plus Python executable SHA-256 and build identity, are recorded and frozen in a private admission manifest before the primary run. `runtime_integrity.py` snapshots these without importing third-party runtimes. The supervisor verifies the full manifest before and after the run; this hashing is charged to the total primary wall time. This identity coverage is the Python executable and files declared by installed Python distributions, not every operating-system library or kernel byte. Missing declared files are explicitly recorded rather than silently invented. No automatic upgrades or dependency changes during the run.
- Baseline: CPU, FP32, `eval()`, inference mode, eager attention, no gradients. Candidate: `torch.ao.quantization.quantize_dynamic(model, {torch.nn.Linear}, dtype=torch.qint8, inplace=False)`, fbgemm, default observer. Every one of the expected 38 Linear modules must be replaced at the same names, with qint8 weights and zero remaining FP32 Linear modules. No silent fallback.
- Only local, hashed safetensors and tokenizer/config data are accepted. `local_files_only=True`, `trust_remote_code=False`, `use_safetensors=True`; config `auto_map`, unlisted files, symlinks, and downloaded code are rejected. No pickle input is loaded. Model loading diagnostics must have zero missing, unexpected, mismatched, or errored keys; no partially random-initialized fallback is accepted. Network-related socket operations are rejected in the worker, and official offline/telemetry flags are set.
- One CPU affinity, the lowest already allowed CPU, shared by supervisor and workers. Torch intra/inter-op and numerical-library thread settings are one. Tokenizer parallelism is disabled. No GPU. Parent and worker run sequentially on that same CPU. No other process or workload is stopped or reconfigured. No bwrap, environment switching, permission bypass, or denied-action retry.
- Official API references: https://docs.pytorch.org/docs/2.5/generated/torch.ao.quantization.quantize_dynamic.html and https://huggingface.co/docs/transformers/v4.57.1/en/model_doc/auto . The API documents weight-only dynamic quantization and the copy implied by `inplace=False`; its transient FP32 copy is charged, not hidden.

## One primary run and bounded resources

Exactly 12 fresh exec-spawned workers form six consecutive paired sessions. Order is FP32, INT8, INT8, FP32 repeated three times, giving alternating AB and BA pairs. No process is forked from an imported model runtime. A worker performs one first request, two full 12-query warmup cycles, one canonical 12-query score pass, then five full timed cycles. Timed cycles rotate their first query by cycle index. Each worker times 60 requests/240 pairs. Across the run there are 720 timed requests/2,880 timed pairs; startup, warmup and canonical work are additional and fully retained in cost records.

The total externally measured primary command wall ceiling is 600 seconds, including supervisor interpreter/import startup, supervisor preflight, all startup and inference, byte-size measurement, and results. Each worker has a 45-second wall ceiling and CPU-time limit. Combined supervisor plus active-worker RSS must remain at most 2 GiB. A 50-ms watchdog uses the sum of process high-water measurements conservatively; final per-exec VmHWM is checked as well. `ru_maxrss` may retain an ancestor peak across exec and is diagnostic only, never the authoritative peak. Linux RSS accounting is approximate, and this is a monitored stop condition, not a hard cgroup reservation or proof of sub-poll instantaneous bounds. It should never be described as such. At first output, service readiness, after inference, and after serialization, record absolute `ru_maxrss`, `/proc/self/status` VmRSS/VmHWM, and smaps_rollup RSS when available. Reference: https://docs.kernel.org/filesystems/proc.html . Report startup-plus-quantization-plus-inference VmHWM separately from the experiment-lifetime VmHWM that also includes the in-memory serialization buffer. Never present that buffer-induced difference as inference-memory savings. No subtracting the parent's RSS to invent model memory. Record CPU model and flags, selected CPU ID and affinity, visible cgroup CPU/memory limits, Python version/build/compiler, kernel, and torch build configuration with the output.

The higher number of fresh sessions is prospectively chosen for order sensitivity; five timed cycles per worker reduce total timed cycles from the initial four-worker sketch. No result informed this choice. If the fixed budget cannot finish, stop with `INCONCLUSIVE_ABORTED_NO_RETRY`; do not reduce sessions, increase resources, change packages, or fix-and-rerun after model output.

`PRIMARY_ATTEMPT.json` is exclusively created before the first worker. Never remove it to retry. Failures and all completed/partial session files remain private and preserved. `failure.json` records the active arm/session, last observed parent and worker VmHWM, combined monitored peak, elapsed worker/primary times, violated bound(s), and exit status; the session log retains runtime errors. A missing runtime or invalid admission before the first model worker is a preflight blocker, not permission to start an alternate experiment. Any later genuinely new experiment requires a separately versioned preregistration and authorization; it cannot replace this outcome.

## Timing and byte accounting

The timing label is **process-cold, OS page-cache uncontrolled**, not disk-cold. Preflight and worker hash verification read model bytes and warm the OS page cache. There is no cache flushing or fake claim of uncached storage. Each worker starts from a fresh interpreter with no model or tokenization cache inherited from a predecessor.

Record three distinct parent-clock durations:
1. Launch to first completed query, including interpreter startup, imports, verification, tokenizer/model load, INT8 conversion where applicable, and first request.
2. Launch to service readiness after both full warmup cycles. This includes first request and warmups, and is the startup charge for the fixed deployment-cost projection.
3. Launch through process exit and usable result JSON read/parse. This includes all setup, warmups, canonical scoring, timed inference, in-memory serialization measurement, output, and teardown. The internal `primary_wall_seconds` begins inside supervisor main, so it includes all 12 workers and supervisor work after that point but not its own interpreter/import startup. The mandatory outer timer below records the complete primary command boundary; do not confuse the two clocks.

Warm request timing includes tokenization, padding/truncation, CPU forward pass, finite-score checks, and score extraction to Python. No pre-tokenized tensor cache is used. Report each worker's mean and nearest-rank p95 query latency, throughput as four times requests divided by summed request duration, and all three length strata. Raw latency samples are retained. Requests and five within-process cycles are dependent repeated observations, not independent experimental units. The six session pairs are the comparison units. No confidence interval, bootstrap significance, or population claim is made.

Report source model file bytes, all allowed source asset bytes, and in-memory `torch.save(model.state_dict())` serialized bytes for each arm. This write-only in-memory state-size measure never loads pickle, never persists weights, and its memory/time is charged. It is not process RSS, actual packed resident memory, network transfer savings, or on-disk deployment savings. Both arms load the same source weight file. Model/runtime acquisition and dependency installation are shared setup costs, recorded separately in admission with elapsed seconds and bytes; they are not silently zero and not included in local process-startup ratios.

Every slower INT8 first response, warmup, full session, higher peak RSS, or unfavorable byte/cost result remains visible. For each session pair, report a 500-request cost projection: readiness milliseconds plus 500 times measured mean warm query milliseconds. This is a fixed linear engineering estimate, not an actual production measurement. Report the break-even query count if warm INT8 is faster; otherwise report no sustained warm saving. No savings number is clipped to appear favorable.

## Prospective gates, no tuning

All gates must pass for every relevant paired session. Missing, nonfinite, failed integrity/resource/replacement, or incomplete outputs are inconclusive, never pass. All scores are raw single-output logits, not sigmoid probabilities.

- Maximum absolute raw-logit difference <= 1.0 and mean absolute difference <= 0.25 over the 48 pairs.
- Tie epsilon is 1e-6 absolute raw logit. A top set contains every passage within epsilon of the maximum. At least 11/12 queries must have overlapping top sets **and** at least 11/12 must have identical complete top sets. An enlarged candidate tie does not count as exact agreement.
- Full-ranking reference denominator consists only of pairs whose FP32 logit difference is at least 0.1. Require at least 36 such passage pairs out of 72 and >= 0.98 same-sign concordance. An INT8 tie against a separated FP32 pair is non-concordant, not dropped. Report all inversions and tie-state changes, as well as per-stratum agreement, without requiring any semantic relevance judgment.
- Across repeated fresh sessions within each arm, maximum score drift <= 1e-6. Exact duplicated passages must tie within epsilon in every session.
- Candidate/reference serialized-state bytes <= 0.75.
- In each of the six session pairs, candidate/reference warm throughput >= 1.10, p95 latency <= 1.05, and projected 500-query total cost <= 1.00.

Thresholds are pragmatic prospective engineering tolerances, not calibrated relevance or statistical thresholds. Small or ambiguous fixture effects must remain small or ambiguous in the report. An all-gate pass is named `PASSES_ENGINEERING_SCREEN_ON_THIS_FIXTURE_AND_HOST_ONLY`; any fully completed gate failure is `DOES_NOT_QUALIFY`. Neither authorizes deployment. No old test result can be combined with this one to create a larger sample.
