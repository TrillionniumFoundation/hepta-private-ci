# Strict SSHSIG and native input ownership

`sshsig_strict.rs` is a bounded cryptographic primitive. It cannot create a trust
anchor, operator acceptance, Root authorization, or original-owner proof. The
existing external policy digest, original allowed-signer bytes, principal,
revocation state, expiry, and durable nonce/replay checks remain authoritative.
On Unix the original inherited-descriptor/OpenSSH verification still runs after
the strict check. Windows production verification remains explicitly
unsupported until actual inherited input handles and original-owner provenance
are admitted; accepting ordinary paths or serialized bytes does not replace it.

The admitted V1 envelope contains the exact magic/version, one pinned raw
Ed25519 key, the expected nonempty namespace, an empty reserved field, SHA256 or
SHA512, and exactly one Ed25519 signature with no trailing packet bytes. The
complete original message is hashed and verified with `verify_strict`. Bounds
are 4 KiB for the packet envelope, 16 KiB for the single allowed-signer line, and
1 MiB for the message. A caller-supplied message digest is never accepted.

An actual OpenSSH-generated signature is tested with both supported hash
algorithms. Twenty-six mutated packet/message/principal cases must be rejected
by the new pipeline. Original OpenSSH independently rejects twenty-four of them.
Its documented reserved-field behavior accepts the other two: OpenSSH ignores
the packet's reserved bytes and reconstructs an empty reserved signed field.
The finite V1 admission explicitly rejects a nonempty reserved field. This is
an intentional stricter-profile difference, not an OpenSSH security advisory.
Standard V1 signatures generated by the original OpenSSH remain accepted.

Original packets and retained receipts are never normalized, silently re-signed,
or upgraded. A non-V1/nonempty-reserved legacy packet requires the original
external policy/signer's review; a rejected stored receipt is not a new grant or
permission to repeat an effect.

The native Windows adapter must consume actual inherited HANDLEs, enforce fixed
role-specific byte limits, and retain the original parent/child owner identity.
A new helper executable selected by an ordinary pathname and a successful exit
code cannot establish that trust. Native ownership must close independently of
this cryptographic primitive. The current Windows failures must remain visible
until that path is implemented and executed on the native runner.
