# 磁盘暂停守护器：计时与费用口径补充

本说明适用于独立的操作守护器启用之后的阶段。它不修改已发布的报告生成器、v3 账本、恢复器、科学源码、协议或测试集合，也不表示尚未运行的确认阶段已经完成。守护器仅按原有阶段命令执行，并可暂停、恢复自己创建的阶段进程组。

## 墙钟保留实际暂停

当磁盘可用空间低于 1 GiB 时，对自有阶段进程组发送 `SIGSTOP`；恢复到至少 2 GiB 后发送 `SIGCONT`。新阶段也须达到启动门槛。该进程组包括阶段 launcher 及继承其进程组的 worker。

原始 `perf_counter` 计时不会因进程被暂停而停表。因此，任何与暂停区间重叠的 chunk、actor、group、worker 或阶段墙钟，都可能包含磁盘暂停、调度等待和其他实际经过时间。守护器自己的阶段墙钟也包含暂停。应保留这些原始数值和独立的暂停事件记录，不把它们描述为无中断服务延迟，也不通过事后扣除暂停重新包装为另一项注册测量。

这些墙钟范围存在嵌套。不得将 actor、group、worker 与守护器墙钟相加，也不得把守护器墙钟作为新增 CPU 费用加入 `RUNTIME_LEDGER_V3.json`。

## CPU 继续使用原有收据

原科学 launcher 通过 `wait4` 获得的 worker 用户态与内核态 CPU 收据仍是对应进程生命周期的 CPU 依据。暂停本身不会增加进程 CPU 使用时间；`process_time`、actor/group 计时仍是嵌套诊断，不重复加入 worker 账。

守护器不通过外层等待时间估算 worker CPU，也不额外叠加 launcher 或守护器的累计子进程 CPU。若某次异常结束未保住原 worker 收据，该次 CPU 仍须按已有账本规则明确为未测或有证据的下界，不能由墙钟补成实测值，不能填零。此说明不声称不同运行条件下的 CPU 数值会逐位相同。

## 注册时间输入与效用不改写

模型和控制器使用数据对象中的公开 `dt` 序列。主执行及新增交叉执行的费用保持为：

`READ_FEE × 已执行读取次数 + TIME_FEE × 对应公开 dt 前缀和`。

`online_confirm.execute_all` 与 `train_execution_cross.validate_arrays` 会按该口径核对保存的费用与效用；效用仍为预测是否正确减去该费用。恢复实验仍使用已登记的读取、重处理、监测、缓存和固定服务时间价格；CPU 与墙钟作为另外的资源记录保存。

操作层暂停不改变这些时间输入、价格、模型权重、动作规则或数据划分，不把真实暂停时间注入 `dt`，也不以守护器墙钟替换效用中的时间项。因此，所报告的是原已登记的有限任务时间与费用语义，不能据此宣称真实在线环境在外部过程持续演化、磁盘停顿或服务排队时的完整净收益。

## 证据边界

本说明依据对 `continue_registered_run.py`、`continue_addendum_v3.py`、三个科学 launcher，以及 `evaluate.py`、`online_confirm.py`、`train_execution_cross.py`、`recovery.py` 的只读源码检查。它不读取正式结果，也不产生新的模型、域、策略选择或统计检验。实际暂停次数和持续时间只能引用守护器随后保存的操作记录；没有记录时不填默认零。
